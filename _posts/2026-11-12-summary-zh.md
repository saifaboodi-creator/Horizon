### [Apache HTTP Server 的 HTTP/2 模块曝严重 RCE 漏洞](https://www.wiz.io/blog/cve-2026-119618-rce-apache-http-server-vulnerability) ⭐️ 8.0/10

据 Wiz 博客文章，Apache HTTP Server 的 HTTP/2 模块（mod\_http2）存在严重远程代码执行漏洞，编号为 CVE-2026-119618，使用该模块的站点运维者需要评估并处置。现有材料未说明触发条件、实际影响范围或官方修复时间表；社区讨论中的版本修复信息也尚未得到独立确认，因此不能把评论中的版本号当作最终结论。

hackernews · soheilpro · 11月12日 02:11 · [社区讨论](https://news.ycombinator.com/item?id=50462177)

**「背景」** 该漏洞位于 Apache HTTP Server 的 HTTP/2 模块 mod\_http2。Wiz 的公告将 Apache HTTP Server 2.4.55 至 2.4.70 列为受影响版本，2.4.71 及更新版本为修复版本；Red Hat 的 CVE 页面还指出，2.0.8 之前的 mod\_http2 不含受影响代码，RHEL 8 及更早版本不受影响。

**「临时缓解需一并停用 certbot 定时任务」** 对启用了 mod\_http2、需要临时停用 httpd 的运维人员来说，仅执行 systemctl disable --now apache2 可能不足以让服务保持关闭：有评论者提醒，certbot 的 cron 任务或 systemd timer 会重新拉起 httpd，必须一并停用，否则缓解措施会失效。就优先级而言，外部检索显示该漏洞 CVSS 评分为 9.8，源于 mod\_http2 并发处理请求头时的同步缺陷，但当时尚未列入 CISA KEV，也没有已确认的在野利用，因此处置顺序应依据实际暴露面和版本核查来确定，而不是依据已发生的攻击。

**「社区讨论」** 评论者对修复版本提出疑问：文章列出已修复的 mod\_http2 为 2.0.24 及更高版本，但受影响范围写到 2.0.42，因此有评论者认为首个修复版本应是 2.0.43；另一条评论给出了指向 apache/httpd 仓库的补丁提交链接。还有运维人员提醒，临时停用 Apache 时需检查 certbot 的 cron 或 systemd 定时任务，因为它可能重新启动 httpd，使“systemctl disable --now apache2”不足以让服务保持停止。

### [AWS 发布官方本地模拟器 aws-emulator](https://simonwillison.net/2026/Nov/11/aws-emulator/) ⭐️ 8.0/10

AWS 已在 GitHub 发布官方 aws-emulator，让开发者在本地克隆的 AWS 服务上运行测试，而无需申请付费 API key。该项目用 Rust 编写；Simon Willison 称项目前三周产生了 29,684 次提交，由大量 AI 代理完成，AWS 的 Swaminathan（Swami）Sivasubramanian 也在 Werner Vogels 的博客上撰文介绍其由来。目前在 macOS 和 Windows 上运行仍需 Docker，Willison 希望未来能改为下载单个二进制文件，并用于其他语言和平台的测试套件。

rss · Simon Willison · 11月11日 21:18

**「背景」** 本地模拟器的用途是在开发机上复现云服务接口，让测试无需创建真实资源或持有付费 API 密钥。AWS 的 GitHub 文档给出的快速开始面向 AI 编码代理：先安装 aws-emulator skill，再让代理完成环境配置（tool-2-1）。在介绍该项目来由的客座文章中，Swami Sivasubramanian 还回顾了团队早年为一套 Amazon 分布式系统搭建高保真模拟环境、用于测试的经历（tool-2-3）。

**「适用范围与限制」** 对想把本地测试搬进 CI 的团队来说，aws-emulator 让集成测试不必再配置付费 API key，但据评论引用的项目安全说明，它不能用来验证 IAM 策略与权限边界、桶等资源策略、KMS 密钥策略以及跨账户或跨区域访问，这些安全控制仍须回到真实 AWS 环境测试。另一个现实约束是 macOS 和 Windows 上目前依赖 Docker，因此 Simon Willison 期待的「下载单个二进制直接嵌入其他语言测试套件」的用法暂时还做不到。

**「社区讨论」** CharlieDigital 对 aws-emulator 是否只是演练、是否会持续维护表示怀疑，并推荐自己使用的 Floci 与 Testcontainers。scriptsmith 则援引项目安全页称，该模拟器不应被用来测试 IAM 策略和权限边界、资源策略、KMS 密钥策略、跨账户或跨区域访问以及其他安全控制。

### [UMAP 0.6 发布：新初始化与优化器加速大规模降维](https://www.reddit.com/r/MachineLearning/comments/1xudaah/umap_06_new_initialization_new_optimizers_and/) ⭐️ 8.0/10

UMAP 0.6 已发布，新增递归初始化方法和新的优化器，并通过更好地利用 PyNNDescent 让最近邻搜索约快 4 倍。维护者称，在 300 万篇 arXiv 论文上完整运行不到 5 分钟，而固定种子的 0.5 版本单线程运行需 52 分钟，约为 12 倍差距；新优化器还让固定种子下的多核运行可复现。新初始化和优化器目前需设置 compatibility\_layout=False 才启用，因为会改变输出，未来版本才计划设为默认；上述性能与质量提升来自维护者自述，尚未独立验证。可通过 pip install -U umap-learn 或 conda-forge 安装。

reddit · r/MachineLearning · /u/lmcinnes · 11月12日 13:51

**「背景」** UMAP 是一个广泛使用的开源降维与流形学习库，用于把高维数据嵌入低维空间；其流程大致分为近邻图构建、初始布局生成，以及基于吸引—排斥的随机优化三步，在大规模数据上近邻搜索长期是耗时的主要部分。此前版本（如 UMAP 0.5）依赖谱初始化或 PCA 提供起点，再由优化器逐步修正，这既让固定种子下的运行只能单线程完成，也使百万级数据上的最终质量在很大程度上受制于初始布局。

**「影响」** 由于新初始化和优化器目前是选择性启用，依赖默认行为的现有流程升级后应确认输出是否保持不变；想测试新功能的用户需显式设置 compatibility\_layout=False，并重新检查聚类结果及固定种子下的可复现性。

### [谷歌发布 Gemini Decisions API，支持音视频与 PDF](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-decisions-api/) ⭐️ 7.0/10

谷歌发布 Gemini Decisions API，基于 Gemini Decision 1 模型，支持是/否、选项和评分规则三类封闭式问题，覆盖文本、图像、音频、视频和 PDF 输入；单次最多可提交 1000 个问题，并返回概率与置信度。定价为每百万输入 token 0.10 美元、输出不收费；谷歌称端到端延迟约 150–250 毫秒，比 Gemini 3.5 Flash-Lite 方案便宜近 5 倍，现已在 Google AI Studio 提供。与 Jev 和 OpenAI 的决策模型相比，Gemini 的多模态范围更广；Jev 仍以 4.2 美分/百万输入 token 更便宜，但只支持文本和 JSON。在 Simon Willison 公布的一段视频测试中，Gemini 对“是/否”问题返回 0.0498、0.9234 等概率值，而不是 Jev 和 OpenAI 那样的 1.0/0.0。

hackernews · iamdelirium · 11月11日 18:32 · [社区讨论](https://news.ycombinator.com/item?id=50456791)

**「背景」** 在 Gemini Decision 1 之前，Jev 和 OpenAI 已提供面向是非、选择和评分等封闭式问题的决策模型，输出概率而非自由文本。Jev 只接受文本和 JSON，OpenAI 可处理文本与图像；Gemini 的差异在于把音频、视频和 PDF 也纳入同类接口。

**「影响」** 对需要从 PDF、音频或视频中做封闭式判断的开发者，Gemini Decisions API 可直接接收原始文件，省去先转写或 OCR 的步骤；但在文本高并发场景下，Jev 的 4.2 美分/百万输入 token 仍是更低成本选项。由于“是/否”返回概率而非布尔值，接入方需要自行设定判定阈值。

### [vLLM-Omni 在 Vera Rubin 上优化 H3-Image 4K 推理](https://vllm.ai/blog/2026-11-12-minimax-h3-image-rubin) ⭐️ 8.0/10

**「方案」** 作者把 4K 推理拆成 DiT 计算、VAE 解码和显存占用三条优化路径。在 Rubin 上，他们把扩散线性层接入 vLLM 的在线 MXFP8 加载，合格 DiT 线性层用 FlashInfer CuTe-DSL MXFP8 GEMM、注意力用 TRTLLM\_ATTN，并用 Ulysses SP4 把序列分到四卡、DiT TP1 复制权重，同时缓存 AdaLN 条件投影，六步去噪仍完整执行。VAE 按瓦片跨卡并行，叠加 CUDA Graph 重放和多流后，四卡 GB300 的 BF16 对照中解码从 2.635 秒降至 0.213 秒，端到端从约 4.0 秒降至 1.6 秒；小显卡则以逐层 CPU offload 换显存，RTX 5090 上 4K 文生图约 52.29 秒。作者报告四卡 SP4 在短提示基准的中位延迟为 0.87 秒（p95 0.944 秒），比 GB200 快 2.21 倍、比 GB300 快 1.64 倍，SP1×DP4 吞吐配置达 6,115 张/小时。但他们明确 0.87 秒来自单独的短提示语料，不同于 1,292 字符咖啡提示的 1.09 秒，跨硬件数字比较的是部署系统而非单一架构；按每图 0.06879 美元的假设售价、满负荷计，四卡峰值毛收入约 105.16 美元/GPU/小时，且未扣运营成本。

**「启示」** 作者认为，扩散服务要把 DiT 计算、VAE 解码和显存放置一起工程化，而头条延迟、吞吐与经济性必须放回各自基准和假设中解读。
